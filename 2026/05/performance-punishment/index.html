前言

這篇文會是尚未出爐的 2026 上半年大大流水帳的其中一個分支，因為狀況實在是太特殊了，所以拉出來單獨講。

主要想記錄的包括：沒有直接拿出來砲轟其他人的事情來龍去脈、個人心理活動、如何不要變成能者、以及不幸變成能者之後要怎麼不在過勞中痛苦地死去。

正文 — 神隊友逐漸浮現

不曾想過，筆者原本平穩順遂的大學分組日常也是開始遇上神隊友了，不如說之前一直沒遇上神隊友簡直是神蹟，前世的我已在佛前求了五百年求祂讓我 GPA 不要爆炸。這次出現的神隊友其實也稱不上多神，只是當下的情況精準刺中了筆者的阿基里斯腱。這個神狀況便是：當專案差不多要進入實質動工階段時，猛然發現除了自己以外，其他組員恰巧完全擠不出時間。

筆者的缺點之一就是濫好人當太多，永遠將團隊目標置於首位，卻忽略了自身的負擔極限以及個人時間的稀缺性。當多數隊友都能配合協作、平行推進進度時，這個缺點就不太會顯現出來；但如果當下只有包含筆者在內的少數隊員有空，這個致命傷就會直接噴血。筆者會不自覺地將遠超自身負荷的工作量全數攬下。最終，任務依然會達標，但代價是換來一個身心俱疲、徹底燃盡的筆者。對心理健康而言，實在是歡喜地吃下幾十劑氰化物劇毒。

抱怨完前提，就要開始抱怨事件本身了。這次將筆者推向極限的事件有二，以下展開：

雙北儀表板黑客松

情境：小組四人，其中兩人直到黑客松前一天才有空，空缺理由符合常理。

開發期間，就算 vibe coding 用得再兇，應當還是要花點時間熟悉這種大型專案的框架和建開發環境。筆者原本甚至是想要提前把 MVP 趕出來，只把空空如也的肚子留給黑客松的；但在人手嚴重不足的狀況下，也只能先把開發流程先跑一遍，以及把可以通用的 LLM 不動點功能做出來，剩下的留給黑客松期間再戰。

但前一天才有空是能讀懂個毛線開發環境啊？

這種情況下，根本沒辦法把核心開發交給那兩人，而這次黑客松又頗缺少前端需要負責的部分。於是小組內只剩下懂全端架構的筆者，跟另外一位同樣懂架構、還已經提前把一堆 LLM 功能開發出來的好隊友。直到前一天才跟遲來的兩個人同步了現況，地獄開局說是。

於是，黑客松第一天就在其他三人海巡可用的 API link，而筆者一人扛下全端儀表板組件開發的重擔，loading 真的是太平衡了（諷刺）。當天也特別感謝清大網路決定躺平，遠端連線延遲高到令人崩潰，試問新北市政府跟清大是有什麼深仇大恨嗎。兩個備份好的遠端環境完全報廢，只能用架在筆者筆電上的又另一個備份環境；然後又特別感謝 Windows 防火牆立大功，把用 Zerotier 內網連線的其他人擋在筆者的筆電外。

筆者原本想要做的主題類別被主辦方駁回，勉強選了一個「可做」但只是妥協後的副產物主題，做到最後卻發現關鍵資料集缺失（新北市政府我謝謝你），晚上 8 點鬼轉主題，留了一堆新組件要開發。至於誰來開發，當然是回飯店洗完澡後又要繼續爆肝的筆者。弄到凌晨時又發現資料集之間對齊上有問題，Codex 也只會像一隻無限猴子般一直寫出 bug。原本訂旅店就是打算這次晚上要好好睡一覺的，如此奢望的夢想在眼下完全幻滅，只能坐在筆電前頂著 Codex 的 5-hour Rate Limit 來回切帳號才能持續開發下去，心態完崩。

p.s. 這次住到的旅店讓筆者的價值觀大開眼界，花的 1300 比不上高雄的 500，跟做公益活動沒兩樣。這建築結構在消防安全上真的沒問題嗎？

幸虧在凌晨 3 點時，距離兩個帳號刷新 rate limit 前空出來了一個小時的空檔，強迫筆者比上次多睡了一小時（所以總共獲得一小時的高品質睡眠），至少起床後不會那麼想要想死了（不誇飾）。理所當然地自我評估了一下現在的半成品效果後，大砍現有方向，繼續做 MVP。頭腦清醒後做起來效率實在是比較高，做到早上 7 點左右時只剩下最後一個組件了。從飯店回比賽場地後繼續開發，最終趕在Demo 前把所有組件都開發校正完成，交由另外一位貌似只睡三小時（貌似在處理 Demo 稿）負責口才擔當組員進行報告。最終很意外地進了決賽，但或許是因為上台時筆者後半段的操作失誤（帳號忘記登），最後還是沒有獲獎，但比上次好。當然，只指成果。

說來也奇怪，筆者到底要用怎麼樣的心態，去面對一整天拼死拼活開發出來的濫竽充數組件竟然有進入決選這件事？心態自從凌晨崩潰後就完全沒有任何期望了，原本甚至已經做好了開天窗的準備。用已經爆炸的心態跟 Codex 乾瞪眼期間，看到 DC 跳出來那個沒辦法被分配任何核心工作的隊友說「沒事的話自己要去睡了」，太荒謬了吧？

這裡有個人不知道自己今晚能不能睡、能睡多久、明天早上會不會開天窗、開天窗的話要怎麼辦等種種全部不知道。但對，沒事的，早上回比賽場地後還要靠著總算有點進度的開發結果當作心理基石，在全部人面前非常冷靜、有說有笑地演戲假裝自己心理狀況沒問題。上學期的戲劇通識課期末演戲沒拿滿分簡直就是奇蹟，要不要乾脆我來教大家怎麼演？

沒有進入決選說不定還輕鬆一點，至少可以獲得一堆的睡眠時間。但這麼說好像對不太起那位負責口頭報告的組員，畢竟進決選大半還是靠她的發揮。

總之，筆者最後連問卷都懶得填就離開了，反正也不會有下一次了。看台上的主辦人員在那邊哭得唏哩花啦，說著一堆不知所云的感謝詞，跟筆者完全無所謂只想快點結束的心態相比，要的就是這種反差感，愛了愛了。複盤、慶功宴的啥都根本沒意義弄；哪裡來的「功」，戴上眼鏡後看到的只不過是筆者用血汗搭建起來搖搖欲墜的現實罷了。團隊合作佔比純純的 $\epsilon$，然後筆者自己的負擔是 $1-C-\epsilon$。這種黑客松誰愛參加誰參加，這問題已經不是溝通就能解決的事了，直接退群比較快，完全正解。

這次的工作分配極度失衡，是兩位成員沒空熟悉架構佐上筆者這個大缺點後熬出來的失敗秘訣精華大骨湯。當初就應該狠下心把工作平均地分配下去（像是一個人開發一個組件），反正環境看不懂、開發不出來也就只是個人的事，不干我任何事。真的沒有必要把其他人原本應該要負責的工作自動幫他換成「可以、適合」負責的欸，更不應該犧牲自己的時間和心理狀態去補救原本就是屬於他人的工作。這問題早在上次就已經出現了，為什麼筆者要等到這次變本加厲後之後才會意識到呢？

哎，為什麼沒辦法在沒空的人身上進行有罪判決呢？提議平台上應該提這種法案才對啊。

反省時間

前面輸出太多了，來點評一下缺點：

  • 剝奪他人的參與權，卻又怪罪他人不參與
    其實應該將開發過程拆分成更多耦合度更低的步驟，才能真正實現平行開發。一個可行的解法是引入 Mock Data，從組件層面先敲定最後要吃的資料格式，接著將工作拆分為前後端雙軌並行。前端先用 Mock Data 進行效果與版面測試；後端則同時指派人手去搞定那些無法平行化的 Airflow DAG / ETL 到 Components 的資料串接。沒有做好這層規劃，確實是筆者在專案管理上的失誤。

  • 溝通缺失導致的「讀心術」期待
    又是另一個筆者痛點，凌晨當下確實只有另一位隊友被筆者硬控到凌晨 3 點才去睡，但筆者中途並沒有明確要求他要做什麼。說到底，應該在早上時覺得事情太多的時候就馬上交接的，或者說，打從一開始就該優先修好防火牆的連線 Bug，沒修好等同於將所有開發 Loading 死鎖在筆者一人身上。或是加入定期每 30 分鐘的問題報告，讓其他人來把筆者這邊的問題認領走；或是建立啥求救協議的。是時候去看些管理部分的書了，再這樣下去只會變成只有筆者受傷的能者過勞世界。

  • 用自己的標準綁架隊友
    這部分筆者就管不到了，每個人的自我要求都不太一樣，如果對方給我的感覺就只有那麼高的話，我也只會以這樣的標準來對你，然後下次把你放生。不過有另一個小解方：把將「能力」與「態度」拆開篩選。把那些極度被動，但只要給明確 SOP，就會像機器人一樣完美執行的人抓來當副手。畢竟人類的能力分佈符合常態曲線，嚴格篩選只會把人篩沒；未來職場工作環境也沒有悠哉挑隊友的餘地。啊但如果是接了工作但沒有實際能力可以做好的人，就只有被丟入黑名單的份。

  • 學會放手
    簡而言之：心安理得地把人當全能的 API Oracle 來用，Oracle 炸了自己想辦法修。

這些反省只要筆者跟 LLM 對談煉丹就夠了。交友跟團隊合作真的是兩回事，筆者勢必又要重新建立自己的交友門檻了，或是應該把交友權限精細度調高一點，現在感覺越來越混在一起了。或是混一點筆者朋友傳授的利益導向交友。反正只要不是像之前道德有瑕疵或是做出什麼違反法律的神人 人？還是太高尚了點，我就看這個案例要被我鞭幾次 的話，交惡門檻設太低不見得是好事。不過總之，全員不通過。

影像處理期末專題

換了一批人馬，同樣的問題重複上演：原本預計有 2 個禮拜可以從容開發的期末專題，3 人小組內依舊有 2 個人在第一個禮拜「完全沒時間」，等同於要在短短一個禮拜內把期末專題硬刻出來。依照筆者過往的經驗，買大樂透刮出頭獎後馬上被雷劈的機率還比較大一些。在這種緊急情況下，筆者仍然是認命地把 MVP 慢慢地做出來了（指兩天內），接著才意識到歷史的重演，失眠一晚後果斷把剩下的進度丟到兩位組員都已經有空的時空去了。幸虧最後報告順序出來後才發現我們又多了一個禮拜可以開發，所以也就是又有 2 個禮拜可以開發了。專案能誕生的機率從完全不可能升級到還過得去。

另外一個有趣的點，筆者在這次專案中把自己定位完全調換了，準備做小實驗 owo。

至少這次筆者有即時停損，沒有讓自己心態跟著原始時空裡的專案一起爛下去，接下來就看另外兩位組員「願意」承擔起多少負責的部分了（或是馬上套用上面反省部分的操作）。真的破事一堆。
